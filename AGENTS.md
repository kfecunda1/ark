# ARK

ARK is a private, two-user tracker for banking-product client projects. It is a from-scratch rebrand of an internal CRM template — no part of it is affiliated with, or should ever reference, that template's original owner, branding, or business lines.

## What ARK tracks

Projects run on a banking product — SBLC, MX103, MT103, IP-IP, API, API Cash, T2T, S2S, VISA, GPI, KTK are the ones seeded by default, but the list itself is admin-managed data now, not a fixed set: see **Settings** below. There is no "business line" concept in ARK.

A project moves through four **stages** — New, Documents Received, Match, Status — and once it reaches Status it also carries a **status**: Open, With Receiver, With Sender, Waiting, In Process, Completed, Lost (`lib/projects.ts`). A project has 1-3 **product options** (`project_products` table) and, once settled, one **final product** (`projects.final_product`, must be one of its own options — a project with exactly one option gets it automatically) — see the Products module below. "Matched With" (a single Receiver, not an internal user) is the only Receiver a project carries; it had a Client Contact and an Assigned Contact too, but both were removed. A project can also be flagged **Recovery** (`projects.is_recovery`), which switches the ratio auto-fill to read the matched Receiver's recovery ratio instead of their normal one, and can carry an optional **Contact Person** (`projects.contact_person_id`, a `people` row). A project also has Ratio Presented/Ratio Real (free text, e.g. "70/30"), a Total Face Value + currency — all manual entry, no profit field, no formulas.

## UI naming vs database naming

What the UI calls **Receivers** is the database's `contacts` table and `Contact` type — unchanged since the template, still every column/FK/bucket named `contact_*`/`contacts_*` (`contacts`, `contact_products`, `contact_documents`, the `contact-documents` storage bucket, `matched_contact_id`, `contact_id`, the `contact`/`contact_product`/`contact_document` activity-log entity types, `lib/actions/contacts.ts`, `lib/contacts.ts`). Only what the user sees — the sidebar label, page titles, `/receivers` routes (old `/contacts` URLs permanently redirect there, see `next.config.ts`), button text, filters, the global-search group, activity-log labels, the Dashboard, the "Matched With" picker, and the Notes link picker's "Receiver" option — was renamed, in `supabase/migrations/016_receivers_and_people.sql` and the app code that followed it.

What the UI calls **Contacts** (the sidebar tab after Receivers) is a separate, genuinely new table: `people`/`Person` (`lib/people.ts`, `lib/actions/people.ts`, `app/(app)/people`, `components/people/*`). It was named `people` specifically so it could never collide with the existing `contacts` table above. A Receiver or a Project can optionally link to one `people` row as its **Contact Person** (`contacts.contact_person_id` / `projects.contact_person_id`, both `on delete set null`) — picked via `components/entity-picker.tsx` (form mode, with inline "+ New contact") or `components/contact-person-select.tsx` (the detail pages' inline quick-editor, same inline create).

## Modules

- **Projects** (`app/(app)/projects`, `lib/projects.ts`, `lib/actions/projects.ts`) — the core pipeline. A project's product options (1-3, `project_products`) are picked on the form; the detail page (`components/projects/project-product-options.tsx`) shows them as chips with "Choose as final" while nothing's decided, or "Rejected" + "Make final instead" on every other option once one is, plus "Undo choice" to go back to Not decided. The ratio auto-fill only runs once a final product exists — before that, the matched Receiver's ratio per option is shown as information only, never written.
- **Matched With** — the single Receiver a project carries (`projects.matched_contact_id`, UI: Receiver — see naming note above); duplicate detection (same matched Receiver + an overlapping product option) is a **warning only**, never blocking a save.
- **Recovery** (`projects.is_recovery`, `contact_products.recovery_ratio`) — a project flagged Recovery reads the matched Receiver's `recovery_ratio` instead of `ratio` for the auto-fill; everything else about the flow (fill-if-empty, Use/Keep on a mismatch, a hint when the Receiver has no ratio of the needed kind on record) is identical to the non-recovery case.
- **Timeline** (`project_steps` table, `lib/actions/project-steps.ts`, `components/projects/project-timeline.tsx`) — the project detail page's own activity log. Two step kinds — **step taken** and **next step** (carries a `due_date`) — plus the project's own `notes` rows (linked via `notes.project_id`) merged into the same feed. Open next steps (not yet done) are pinned at the top, earliest due date first; everything else — step-taken, notes, and next steps once checked off — lives in the full history below, newest first. Checking a next step's "Done" box sets `done`/`done_at` and moves it into history with a strikethrough; unticking reverses it. Every entry supports inline edit and delete (delete asks for confirmation). Due dates are colored by `lib/projects.ts`'s `dueDateTone()`: red = overdue, amber = due today, neutral = upcoming — shared with the Projects list's "Next Step" column and the Dashboard's "Due today & overdue" section.
- **Tranches** — each project has Tranche 1 and 2 always visible on its detail page, plus a "Tranches after" flow to add 3, 4, …; each tranche has a manual amount and a "sent on" date (empty = not sent). `project_tranches` table, `components/projects/tranches-section.tsx`.
- **Receivers** (`app/(app)/receivers`, UI name — see naming note above) — people linked to projects, with free-text capability tags and an optional Contact Person link.
- **Contacts** (`app/(app)/people`, backed by the `people` table — see naming note above) — simple person records (first/last name, phone, email) that a Receiver or a Project can optionally link to as its Contact Person. List is searchable and sortable by name/created; the detail page shows every Receiver and Project currently linked to it. Creating one warns (never blocks) on the same email or the same first+last name already on record.
- **Notes** (`app/(app)/notes`) — free-form notes and reminders, optionally linked to a project, a Receiver, or nothing. A project-linked note also shows up in that project's own Timeline (above); a reminder with a due date today or earlier also surfaces in the Dashboard's "Due today & overdue" section.
- **Activity** (`app/(app)/activity`, `lib/activity.ts`) — an audit log of created/updated/deleted rows across projects, Receivers, Contacts (people), documents, notes, and timeline entries.
- **Documents** — file upload with SHA-256 duplicate detection, attached to a project (`lib/storage.ts`, `lib/actions/projects.ts`). Document types — CIS, POF, DOA, PGL, JSON, Proof of Fulfillment, Supporting Documents, Additional Documents are the seeded defaults — are admin-managed data; see **Settings** below.
- **Global search** (`components/global-search.tsx`, `lib/search.ts`) — searches projects, Receivers, Contacts (people), documents, and notes.
- **Sorting** — the Projects, Receivers, and Contacts lists are sortable (`sort`/`dir` URL params, kept alongside the filters): click a column header on desktop, or use the "Sort by" dropdown + direction toggle on mobile (`components/sort-controls.tsx`, `lib/sort.ts`). Empty values always sort last, in either direction. Defaults: Projects by Next Step Due (soonest first), Receivers and Contacts by Name (A-Z).
- **Dashboard** (`app/(app)/dashboard`) — "Due today & overdue" (open next steps and note reminders due today or overdue, across every non-archived project, with a Done checkbox right there), an Open Recovery Projects count, and Stuck Projects (open, non-archived, non-closed projects with no activity in 7+ days, oldest first — the threshold comes from Settings → Defaults).
- **Settings** (`app/(app)/settings`) — **Products** and **Document Types** (admin only): Add, Rename, Hide/Show, and reorder. These replaced the old hard-coded `PRODUCT_TYPES`/`DOCUMENT_TYPES` lists — both are now rows in the `products`/`document_types` tables (`lib/products.ts`, `lib/document-types.ts`, `lib/actions/catalog.ts`), read by every dropdown, filter, and the Dashboard's product breakdown. Hiding an item removes it from *new-entry* pickers only — existing projects/Receivers/documents that already use it keep displaying and filtering correctly; nothing is ever deleted, only hidden. Renaming cascades automatically (`ON UPDATE CASCADE` on the FK from `project_products.product`/`contact_products.product_type`/`project_documents.document_type`/`contact_documents.document_type`). **Defaults** (admin only): default currency for new projects, and the Dashboard's "stuck after N days" threshold (`app_settings`, a single-row table, `lib/app-settings.ts`). **My Profile** (everyone): display name. A user's `role` column (`admin`/`member`/null, gated by `is_admin()`) is what the first three sections check — only an admin sees them, and a non-admin can never change their own role through the app (enforced by a DB trigger, not just UI).

"Add anyway" always proceeds past a duplicate-detection warning — see Matched With and Contacts above.

## Database

The real ARK schema lives in `supabase/migrations/001_ark_schema.sql` — run it once, by hand, in the ARK project's Supabase SQL editor. `supabase/verify_ark.sql` has read-only checks to run afterwards (RLS enabled everywhere, no policy grants to `anon`, the `project-documents` bucket exists and is private). Everything under `supabase/_jes3_archive/` is the history of the template this app was copied from — it was never run against ARK's database and never will be; it's kept only as reference.

Every table uses the same pattern: RLS enabled, policies gated on `is_registered_user()` (a Supabase Auth user becomes "registered" only once they have a `profiles` row — the app creates it on first login). For a private two-user tool, that means signups must also be disabled at the Supabase Auth level; `is_registered_user()` is the second lock on the door, not the first.

Do not run database commands or migrations outside of a deliberate, reviewed step like this one.

## Removed from the template

Telegram integration, the Procedures module (and procedure-to-lead matching), wallets/crypto fields, and all non-banking business lines (crypto, gold, PGM, oil products) were removed in Phase 1. The old `leads`-table field set (`procedure_type`, `deal_value`, `source`, `follow_up_date`, `assigned_to`→profiles, `stage_updated_at`, boolean `archived`) was replaced in Phase 2 by the field set described above. Kept throughout: Contacts (renamed Receivers in the UI — see naming note above), Notes, document upload with duplicate detection, global search, activity log, mobile layouts, login.
